# 01. 기획 — 패스키로 잠근 소개 페이지 (과제 8)

## 목표

과제 1의 소개 페이지 `webtest` 에 "비밀번호 없이 나만 들어가는 자리"를 붙인다.
공개 소개(`/`)는 지금처럼 누구나 보고, 새로 만든 `/private` 만 패스키로 잠근다.

## 스택 선택

| 항목 | 선택 | 이유 |
|---|---|---|
| 프레임워크 | Next.js 16 (App Router) | 정적 사이트로는 challenge 발급·검증·세션이 불가능. webtest 공개 콘텐츠는 그대로 이식 |
| WebAuthn 크립토 | `@simplewebauthn/server` v13 (서버) + `@simplewebauthn/browser` v13 (브라우저) | COSE/CBOR 파싱·attestation/assertion 검증은 직접 짜면 오류 위험이 큼. 검증된 라이브러리에 위임 |
| 로그인 방식 | usernameless / discoverable (`residentKey:"required"`, `allowCredentials` 생략) | 아이디 입력칸조차 없어 "비밀번호 칸 없음"(C35)이 확실. 브라우저가 패스키 선택 UI 표시 |
| "계정" | 회원가입 없음. 패스키를 처음 등록하면 그 사람 몫의 "비공개 자리"가 생김 | 과제 C36·C42 의 "계정" = 이 자리. 이름·이메일·비밀번호 입력 없음 |
| 등록 시 입력 | 패스키 이름(label) 텍스트 1칸 | C24 "사람이 알아볼 수 있는 이름". 비밀 아님, 자동 제안값 채워둠 |
| 비공개 콘텐츠 | 로그인 후 비공개 화면에서 직접 항목 추가·삭제 (수정 없음) | C14 3개 이상, C36 자리마다 다른 내용 |
| 세션 | 불투명 난수 토큰 → `HttpOnly`+`SameSite=Lax`+`Secure`(prod)+7일 쿠키. KV 에는 `sha256(token)` 만 | 로그아웃·자리 삭제 시 KV 키를 지워 즉시 폐기 |
| 저장소 | Redis (Vercel Marketplace 통합 → Redis Cloud, TCP). 클라이언트 `ioredis`, 접속은 `REDIS_URL`. 관계형 DB 아님 | challenge 의 TTL·1회 소비가 `SET EX` + `GETDEL` 로 깔끔. `schema.sql`·마이그레이션 불필요 |

### 검토했지만 고르지 않은 것

- **크립토 직접 구현** — COSE 키 파싱·서명 검증 버그 위험이 크고 검증 시간이 늘어남.
- **Auth.js / Clerk / Hanko / Passage** — 외부 인증 서비스 의존이 생기고, 토큰 만료 전 즉시 폐기를 별도 설계해야 함.
- **Postgres(Supabase 등)** — `schema.sql`·접속 문자열·풀러 설정 등 설정 대비 이득이 적음. challenge 1회성도 KV 가 더 단순.
- **비밀번호 폴백 / 이메일 복구** — 과제 범위 밖. 복구 수단 부재는 "아직 못 막은 것"으로 명시.

## 저장소(KV) 키 구조

| 키 | 값 | 비고 |
|---|---|---|
| `space:{spaceId}` | `{ userHandle(b64url), createdAt }` | 비공개 자리 = 이 키 하나 |
| `handle:{userHandleB64}` | `spaceId` | 로그인 시 `response.userHandle` 교차 확인 |
| `cred:{credentialId}` | `{ spaceId, publicKey(b64), counter, deviceType, backedUp, transports[], aaguid, label, createdAt, lastUsedAt }` | **공개키 저장.** 개인키 없음 |
| `space:{spaceId}:creds` | credentialId 들의 SET | 패스키 목록 / excludeCredentials / 마지막 1개 판정 |
| `challenge:{id}` | `{ purpose, challenge(b64url), spaceId?, regUserHandle?, rpId, createdAt }` | `EX 300`. 소비 = `GETDEL`(원자적 1회) |
| `challenge:audit` | 최근 발급 목록 (capped 200): `{ purpose, at, head:앞16자 }` | "challenge 가 매번 다르다"의 서버측 로그 |
| `session:{sha256(token)}` | `spaceId` | `EX 604800`. 쿠키엔 원문, KV엔 해시만 |
| `space:{spaceId}:sessions` | 토큰 해시 SET | 자리 삭제 시 전 세션 일괄 삭제 |
| `space:{spaceId}:items` | itemId 들의 LIST (입력 순서) | |
| `item:{itemId}` | `{ spaceId, content(≤500자), createdAt }` | 자리별 격리 대상 |

**비밀번호/해시 키는 어디에도 없다.**

## 흐름 요약

### 등록 (첫 자리 생성)

1. `/login` [패스키로 비공개 자리 만들기] → `POST /api/webauthn/register/options`
2. 서버: `userHandle = randomBytes(16)`. `generateRegistrationOptions(...)`. challenge 를 KV `challenge:{id}` (EX 300) 에 저장, `challenge:audit` 에 앞 16자 기록. `id` 를 익명 쿠키 `to8_webauthn` 에.
3. 브라우저: `startRegistration()` → 인증기가 키쌍 생성, 개인키+user handle 을 resident key 로 저장. `RegistrationResponseJSON` 반환. **개인키는 인증기 밖으로 안 나감.**
4. `POST /api/webauthn/register/verify { response, label }`
5. 서버: `challenge.consume(id, "register")` = `GETDEL`. nil → 400. `verifyRegistrationResponse({ expectedChallenge: 저장값, ... })`.
6. 성공 → `space:{uuid}` 생성 + `cred:{credentialId}` 에 **공개키** 저장 + `space:{id}:creds` SADD. `createSession(spaceId)`.

### 2번째 패스키 등록

같은 엔드포인트. 세션이 있으면 `excludeCredentials` 에 기존 패스키를 넣고, challenge 에 `spaceId`·기존 `userHandle` 을 실어 같은 자리에 매핑. verify 는 새 자리·세션 없이 `cred:*` 만 추가.

### 로그인 (usernameless)

1. `POST /api/webauthn/authenticate/options` — `allowCredentials` 생략. 새 challenge.
2. 브라우저: `startAuthentication()` → 사용자가 패스키 선택 → challenge 서명.
3. `POST /api/webauthn/authenticate/verify { response }`
4. 서버: `GETDEL` 로 challenge 소비. `cred:{response.id}` 조회 → 없으면 400. `verifyAuthenticationResponse({ credential: { publicKey: 저장 공개키, counter, ... } })` — **저장된 공개키로 서명 검증**. 실패 → 401.
5. `response.userHandle` ↔ `cred.spaceId` 교차 확인. 카운터 갱신. `createSession(cred.spaceId)`.

### 로그아웃 / 자리 삭제

- 로그아웃: `DEL session:{hash}` + 쿠키 삭제.
- 자리 삭제: `private_item`·`cred`·`session` 키 전부 + `space`·`handle` 키 삭제.

## 자리 간 격리 (C36–C41)

- 자리 ID 는 `lib/session.ts:getSessionUser()` (쿠키 전용) 에서만 온다. URL·헤더·본문에서 읽지 않는다.
- `lib/repository/item.ts` 의 모든 함수가 첫 인자로 `spaceId` 를 받고, 키를 항상
  `space:{spaceId}:items` / `item:{id}`(소유자 확인 후) 로만 만든다.
- 단건 삭제는 `item.spaceId === 세션 spaceId` 확인 후에만 실행. 아니면 404(존재를 숨김).
- 응답은 `lib/dto/records.ts` 화이트리스트를 거친다 — `spaceId`·`publicKey`·`counter` 는 응답에 없다.
