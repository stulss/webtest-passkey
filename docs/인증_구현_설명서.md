# 인증 구현 설명서 — 패스키로 잠근 소개 페이지 (과제 8)

> 이 문서와 `evidence/` 어디에도 실제 개인정보·비밀값(세션 원문, KV 토큰, 개인키, user handle 원문)을
> 남기지 않았다. 검증에 쓴 자리·항목은 검증 직후 정리했다(로컬 인메모리 KV 는 서버 재시작 시 초기화).

---

## ① 무엇으로 붙였나

- **패스키(WebAuthn)**. 비밀번호는 만들지 않았다. 로그인 화면에도, 코드에도, DB에도 비밀번호 칸·해시가 없다.
- **라이브러리 사용**: 서명 검증(암호화 부분)은 `@simplewebauthn/server` v13,
  브라우저 호출은 `@simplewebauthn/browser` v13. attestation/assertion 검증, COSE 공개키 파싱,
  base64url 변환을 이 라이브러리가 한다.
- **세션은 직접 구현**: 로그인 뒤 사람을 알아보는 것은 서버가 직접 만든 **불투명 난수 세션**이다.
  쿠키에는 `randomBytes(32)` 원문, 저장소에는 그 `sha256` 해시만 둔다. 서명 토큰(JWT)이 아니다.
- **앱**: Next.js 16 (App Router). 과제 1의 정적 소개 페이지를 Next 로 옮기고 `/private` 를 더했다.
- **저장소**: Upstash Redis (Vercel Marketplace 통합). 관계형 DB 아님. 로컬에서 자격증명이 없으면
  인메모리 KV 로 폴백한다(개발 편의, 프로덕션에서는 불가).

## ② 왜 그걸 골랐나

- **패스키** — 과제가 "비밀번호를 아예 쓰지 않고 잠그기"다. 공개키 + 일회용 challenge + 기기 분실 대비가 한 묶음.
- **`@simplewebauthn`(라이브러리)** — WebAuthn 크립토는 CBOR/COSE 파싱과 ECDSA 서명 검증이라
  직접 짜면 미묘한 버그가 나기 쉽다. 검증된 라이브러리에 위임하고, 대신 세션·격리·검증 스크립트에 시간을 썼다.
- **직접 구현 서버 세션** — 로그아웃·자리 삭제 즉시 서버에서 폐기해야 해서, 만료 전까지 유효한 서명 토큰 대신
  KV 키를 지우면 끝나는 방식을 택했다.
- **usernameless / discoverable 패스키** — 아이디 입력칸조차 없어 "비밀번호를 입력하는 칸이 없다"가 확실하다.
  브라우저가 저장된 패스키 목록을 띄우고 사용자가 고른다.
- **회원가입 없음** — 패스키를 처음 등록하면 그 사람 몫의 "비공개 자리"가 하나 생긴다. 과제의 "계정"이 이것이다.
- **저장소 = KV(Redis)** — challenge 의 5분 만료와 1회 소비가 `SET EX` + `GETDEL` 로 한 줄이다.
  스키마·마이그레이션·커넥션 풀러 설정이 없다.

**검토했지만 고르지 않은 것**

- 크립토 직접 구현 — 검증 시간·버그 위험이 큼.
- Auth.js Credentials / Clerk / Hanko / Passage — 외부 인증 서비스 의존이 생기고, 즉시 폐기를 따로 설계해야 함.
- Supabase Postgres — `schema.sql`·접속 문자열 2종·풀러 설정 등 이 규모엔 이득 대비 설정이 많음.
- 비밀번호 폴백 / 이메일 복구 — 과제 범위 밖. 복구 수단 부재는 ⑥에 밝힘.

## ③ 어디를 어떻게 고쳤나 — 네 흐름이 지나는 소스

| 흐름 | 화면 / API | 소스 경로 체인 |
|---|---|---|
| **등록** (첫 자리 생성 / 2번째 패스키) | `/login` 또는 `/private` → `POST /api/webauthn/register/options` → `POST /api/webauthn/register/verify` | `app/login/page.tsx`·`app/private/passkeys.tsx` → `app/webauthn-client.ts` → `app/api/webauthn/register/options/route.ts`·`.../verify/route.ts` → `lib/service/auth.ts`(`registerStart`/`registerFinish`) → `lib/webauthn.ts` → `lib/repository/{challenge,user,credential}.ts` |
| **로그인** | `/login` → `POST /api/webauthn/authenticate/options` → `.../verify` | `app/login/page.tsx` → `app/webauthn-client.ts` → `app/api/webauthn/authenticate/{options,verify}/route.ts` → `lib/service/auth.ts`(`authenticateStart`/`authenticateFinish`) → `lib/webauthn.ts`(`verifyAuthenticationResponse`) → `lib/repository/{challenge,credential}.ts` → `lib/session.ts:createSession` |
| **로그아웃** | `POST /api/auth/logout` | `app/private/passkeys.tsx` → `app/api/auth/logout/route.ts` → `lib/session.ts:destroySession` → `lib/repository/session.ts:removeOne` (KV `DEL session:{hash}`) |
| **비공개 자료 조회** | `/private`, `GET /api/items` | `proxy.ts`(쿠키 유무 1차 관문) → `app/private/page.tsx`(`requirePageUser`) 또는 `app/api/items/route.ts`(`getSessionUser` → `unauthorized()`) → `lib/service/item.ts` → `lib/repository/item.ts`(키를 항상 `space:{세션 spaceId}` 로만) → `lib/dto/records.ts`(화이트리스트) |

- 자리 ID(`spaceId`)는 `lib/session.ts:getSessionUser()`(쿠키 전용)에서만 온다. URL·헤더·본문에서 읽지 않는다.
- challenge 검증은 항상 KV 저장값(`expectedChallenge`)으로 한다. 소비는 `lib/repository/challenge.ts:consume` = `GETDEL`.
- 단건 삭제는 `item.spaceId === 세션 spaceId` 확인 후에만. 아니면 404(존재를 숨김).

## ⑤ AI와 나 (요약, 전문은 `AI_3줄.md`)

- **AI에게 맡긴 일**: webtest 정적 사이트의 Next.js 이식, `@simplewebauthn` 연동, 세션·자리 격리 로직,
  소프트웨어 인증기와 자동 검증 스크립트, 문서 초안.
- **내가 직접 판단한 일**: "회원가입 없이 패스키 등록 = 비공개 자리 생성" 모델, 등록 입력은 패스키 이름 1칸,
  비공개 항목은 추가·삭제만(수정 없음), 마지막 패스키 삭제 금지, 저장소를 Postgres 대신 KV, 새 저장소·Vercel 분리.
- **AI 제안을 따르지 않은 일**: AI가 처음 넣은 "계정 이름 입력칸"과 "노트 수정 기능(CRUD)"을 과제 범위 밖으로
  보고 걷어냈다. 비밀번호 폴백·이메일 복구 제안도 범위 밖으로 두고, 복구 수단 부재를 ⑥에 명시했다.

## ⑥ 아직 못 막은 것 (구체적으로)

1. **비공개 자리 복구 수단이 없다.** 등록한 기기를 모두 잃으면 그 자리와 항목에 영원히 접근할 수 없다.
   이메일·복구코드가 없기 때문이다. 운영 서비스라면 복구 코드나 관리자 복구가 필요하다.
2. **레이트리밋이 없다.** `/api/webauthn/*/options` 를 무제한 호출할 수 있어 KV 쓰기·`challenge:audit`
   증가를 유발한다(각 challenge 는 5분 TTL 로 자동 소멸하지만 요청 자체는 못 막는다).
3. **`userVerification` 을 `preferred` 로 두었다.** 잠금 해제된 기기를 그대로 훔치면 지문·PIN 없이도
   인증될 수 있다. 호환성을 위해 `required` 대신 택했다.
4. **`attestationType` 이 `none` 이다.** 어떤 인증기가 만든 패스키인지 검증하지 않는다(개인 사이트라 수용).
   따라서 "이 패스키가 어디에 저장됐는지" 문구는 flags/transports 휴리스틱이라 틀릴 수 있다.
5. **CSRF 토큰이 없다.** `SameSite=Lax` 쿠키 + JSON content-type + WebAuthn 의 origin 바인딩에 의존한다.
6. **인메모리 KV 폴백은 로컬 전용이고 한 프로세스가 죽으면 사라진다.** 프로덕션에서는 절대 쓰이지 않도록
   `NODE_ENV==="production"` 이면 예외를 던진다.
