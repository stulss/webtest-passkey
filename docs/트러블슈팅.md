# 트러블슈팅 (과제 8) — 실제로 겪은 것만

형식: 문제 → 시도 → 비교 → 해결 → 배운 점

---

## 1. `@vercel/kv` 가 설치하자마자 deprecated 경고

- **문제**: `npm install @vercel/kv` 하니 "Vercel KV is deprecated. Upstash Redis 로 이동됨" 경고.
- **시도**: Vercel 문서 확인 → 신규 프로젝트는 Marketplace 의 Redis 통합을 쓰라고 안내.
- **비교**: (a) 경고 무시하고 `@vercel/kv` 유지 vs (b) `@upstash/redis` 로 교체.
  후자가 API 도 거의 같고 통합이 주입하는 환경변수도 호환된다고 판단.
- **해결**: `@upstash/redis` 로 교체. (→ 이 판단은 6번에서 다시 뒤집힌다.)
- **배운 점**: "Vercel KV" 는 이제 제품이 아니라 옛 이름. 계획 때 확인했어도 설치 시점에 다시 봐야 한다.

## 2. 로컬에 Redis 가 없어 아무 흐름도 눈으로 못 봄

- **문제**: 배포 전이라 Redis 인스턴스가 없어 `kv()` 호출마다 예외. `npm run dev` 로 화면 확인 불가.
- **시도**: 로컬 Redis 설치 vs 인메모리 폴백.
- **비교**: 로컬 설치는 작업자(다른 AI 포함)마다 환경이 달라 재현이 어렵다. 인메모리는 쓰는 명령의
  부분집합만 구현하면 되고 프로덕션에서 못 켜지게 막을 수 있다.
- **해결**: `lib/kv-memory.ts` — `get`/`set(ex)`/`getdel`/`sadd`/`smembers`/`scard`/`lpush`/`rpush`/
  `lrange`/`lrem`/`llen`/`ltrim`. `lib/kv.ts` 는 접속 문자열이 없고 `NODE_ENV!=="production"` 일 때만
  폴백하고, 프로덕션이면 예외를 던진다.
- **배운 점**: 개발용 폴백은 "프로덕션에서 절대 못 켜지게" 하는 가드가 폴백 자체보다 중요하다.

## 3. 인메모리 KV 가 요청마다 초기화되는 것처럼 보임 (로그인 직후 401)

- **문제**: `register/verify` 는 201 로 세션 쿠키까지 주는데 바로 다음 `GET /api/passkeys` 가 401.
  서버 로그에 `[kv] 인메모리 KV 로 실행합니다` 경고가 요청마다 여러 번 찍힘.
- **시도**: 세션 쿠키 파싱·해시 계산을 의심 → 실제로는 KV 인스턴스가 라우트마다 달랐다.
- **비교**: Next dev(Turbopack)는 라우트를 따로 번들해서 모듈 스코프 싱글턴(`let mem`)이 공유되지
  않을 수 있다. `globalThis` 에 붙이면 한 프로세스 안에서 확실히 하나가 된다.
- **해결**: 인스턴스를 `globalThis.__to8_memkv__` 에 저장.
- **배운 점**: "서버 프로세스 하나 = 모듈 하나"라는 가정은 개발 서버에서 깨진다. 프로세스 전역 상태가
  필요하면 처음부터 `globalThis`.

## 4. Next.js 16 이 `middleware` 를 deprecated 로 경고

- **문제**: `next dev` 로그에 `The "middleware" file convention is deprecated. Please use "proxy" instead.`
- **시도**: 계속 써도 동작은 한다(내부에서 이미 proxy 로 취급). 하지만 제출물은 최신이어야 함.
- **비교**: 파일명·export 이름을 바꾸기 vs 경고를 안고 가기.
- **해결**: `middleware.ts` → `proxy.ts`, `export function middleware` → `export function proxy`.
  `config.matcher` 는 그대로. (바꾸는 중 잠깐 export 이름이 안 맞아 500 이 났는데, 브라우저 콘솔에
  그 오류가 남아 있어 이미 고친 뒤에도 문제인 줄 알았다. 서버 로그와 `curl` 로 현재 상태를 다시 확인.)
- **배운 점**: 브라우저 콘솔은 **이력**이다. 지금 상태는 서버 로그·curl 로 확인해야 한다.

## 5. `node --test` 가 `@/` 경로를 못 풂

- **문제**: `lib/repository/item.ts` 를 직접 import 하는 단위 테스트가 `Cannot find package '@/lib'`.
- **시도**: tsconfig `paths` 는 타입 검사·번들러용이지 Node 런타임 해석에는 안 쓰인다.
- **비교**: `tsconfig-paths` 의존성 추가 vs import map vs 테스트 범위 조정.
- **해결**: 순수 함수(`lib/domain/rules.ts`)는 `node --test`, 라우트 규약은 소스 정적 검사
  (`test/routes.test.mjs`, fs 만). 저장소 동작 검증은 실행 서버를 때리는 `scripts/verify-webauthn.mjs`.
- **배운 점**: 얇은 도구를 억지로 늘리기보다 검증 종류에 맞는 도구를 나눈다.

## 6. 배포는 됐는데 등록만 500 — Vercel 이 준 Redis 에 REST 엔드포인트가 없었다

- **문제**: `https://webtest-passkey.vercel.app` 에서 `/`·`/login`·`/private`·`/api/items` 는 정상
  (200/200/307/401)인데 `POST /api/webauthn/register/options` 만 `500 {"error":"저장하지 못했습니다"}`.
- **시도**: `vercel env ls` 로 확인 → `KV_REST_API_URL`/`KV_REST_API_TOKEN` 은 통합보다 **5분 먼저**
  등록돼 있었고(= `.env.example` 플레이스홀더), 통합이 실제로 준 것은 `REDIS_URL` 하나였다.
  그 호스트가 `...db.redis.io:18856` — Upstash 가 아니라 **Redis Cloud**, 즉 TCP 전용이고 REST 가 없다.
- **비교**: (a) Vercel 에서 Redis Cloud 를 지우고 Upstash 로 다시 프로비저닝(코드 무변경, 사용자 콘솔 작업)
  vs (b) 이미 있는 `REDIS_URL` 로 말하도록 클라이언트 교체(`ioredis`, 코드 한 파일).
  이미 붙어 있는 저장소를 그대로 쓰는 (b)가 콘솔 왕복이 없고 벤더 REST 에 묶이지도 않는다.
- **해결**: `lib/kv.ts` 를 `ioredis` 어댑터로 교체. `@upstash/redis` 의 자동 JSON 직렬화를 잃으므로
  어댑터에서 `get/set/getdel/lpush/rpush/lrange/lrem` 에 `JSON.stringify`/`parse` 를 넣고,
  SET 계열(`sadd`/`smembers`)만 평문 id 로 둔다. 연결은 `globalThis` 싱글턴(3번과 같은 이유 +
  서버리스에서 호출마다 TCP 를 새로 열지 않기 위해).
- **배운 점**: "Vercel Storage 의 Redis" 는 한 제품이 아니다. 어떤 벤더가 붙었는지는
  **접속 문자열의 호스트**를 봐야 안다. 그리고 환경변수는 이름만 맞다고 값이 맞는 게 아니다 —
  등록 시각(통합보다 먼저 생김)이 플레이스홀더라는 단서였다.

## 7. 로그인 누르면 Windows 가 곧장 "보안 키를 USB 포트에 삽입하십시오"

- **문제**: 실기기로 등록해 보려는데 Windows 보안 대화상자가 지문·PIN 대신
  USB 보안 키 삽입 화면으로 바로 넘어갔다.
- **시도**: `POST /api/webauthn/authenticate/options` 응답을 직접 확인 →
  `allowCredentials` 가 없고(usernameless 라 의도한 것) `hints` 도 없었다.
  힌트가 없으면 Windows 의 네이티브 WebAuthn 이 빈 allowList 요청을 보안 키 경로로 해석한다.
- **비교**: (a) `authenticatorSelection.authenticatorAttachment: "platform"` 으로 **제한**
  vs (b) WebAuthn L3 의 `hints` 로 **순서만 제안**.
  (a)는 폰(QR)·보안 키 등록을 아예 막아 "패스키 2개 · 기기 분실 대비"(C42/C44)를 해친다.
- **해결**: 등록·로그인 옵션에 `hints: ["client-device", "hybrid", "security-key"]` 추가.
  윈도우 헬로/구글 비밀번호 관리자 → 폰 QR → USB 순으로 제안되고, 제한이 아니라서
  보안 키를 쓰고 싶으면 여전히 고를 수 있다.
  `generateAuthenticationOptions` 는 `hints` 를 입력으로 받지 않아 반환값에 얹었고,
  `@simplewebauthn/browser` 가 옵션 객체를 그대로 spread 해서 브라우저까지 전달된다.
- **배운 점**: "선택지를 좁혀서 고치기"와 "순서를 제안해서 고치기"는 결과가 다르다.
  과제 요구(기기 2개)가 걸려 있으면 제한 대신 제안을 골라야 한다.
