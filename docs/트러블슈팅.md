# 트러블슈팅 (과제 8) — 실제로 겪은 것만

형식: 문제 → 시도 → 비교 → 해결 → 배운 점

---

## 1. `@vercel/kv` 가 설치하자마자 deprecated 경고

- **문제**: `npm install @vercel/kv` 하니 "Vercel KV is deprecated. Upstash Redis 로 이동됨" 경고.
- **시도**: Vercel 문서 확인 → 신규 프로젝트는 Marketplace 의 Redis(Upstash) 통합을 쓰라고 안내.
- **비교**: (a) 경고 무시하고 `@vercel/kv` 유지 vs (b) `@upstash/redis` 로 교체.
  `@upstash/redis` 는 API 가 거의 동일하고(`get`/`set`/`getdel`/`sadd`/`lrange`…) Vercel 통합이 주입하는
  환경변수도 호환된다.
- **해결**: `@upstash/redis` 로 교체. `lib/kv.ts` 가 `KV_REST_API_*` 와 `UPSTASH_REDIS_REST_*` 둘 다 읽도록 함.
- **배운 점**: "Vercel KV" 는 이제 제품명이 아니라 Upstash Redis 통합의 옛 이름. 계획 단계에서 최신 문서를
  확인했어도 패키지 설치 시점에 한 번 더 확인해야 한다.

## 2. 로컬에 Redis 자격증명이 없어 아무 흐름도 눈으로 못 봄

- **문제**: 배포 전이라 Upstash 인스턴스가 없어서 `kv()` 호출마다 예외. `npm run dev` 로 화면 확인 불가.
- **시도**: 로컬용 Redis 설치 vs 인메모리 폴백.
- **비교**: 로컬 Redis 설치는 팀원(다른 AI 포함)마다 환경이 달라 재현이 어렵다. 인메모리는
  `@upstash/redis` 가 쓰는 메서드의 부분집합만 구현하면 되고, 프로덕션에서는 절대 안 쓰이게 막을 수 있다.
- **해결**: `lib/kv-memory.ts` — `get`/`set(ex)`/`getdel`/`sadd`/`smembers`/`scard`/`lpush`/`rpush`/`lrange`/
  `lrem`/`llen`/`ltrim` 구현. `lib/kv.ts` 는 자격증명이 없고 `NODE_ENV!=="production"` 일 때만 폴백,
  프로덕션이면 예외를 던진다.
- **배운 점**: 개발용 폴백은 "프로덕션에서 절대 못 켜지게" 하는 가드가 폴백 자체보다 중요하다.

## 3. 인메모리 KV 가 요청마다 초기화되는 것처럼 보임 (로그인 직후 401)

- **문제**: `register/verify` 는 201 로 세션 쿠키까지 주는데, 바로 다음 `GET /api/passkeys` 가 401.
  서버 로그에 `[kv] 인메모리 KV 로 실행합니다` 경고가 요청마다 여러 번 찍힘.
- **시도**: 세션 쿠키 파싱·해시 계산을 의심 → 실제로는 KV 인스턴스가 라우트마다 달랐다.
- **비교**: Next dev(Turbopack)는 라우트를 따로 번들해서 모듈 스코프 싱글턴(`let mem`)이 공유되지 않을 수
  있다. `globalThis` 에 붙이면 한 프로세스 안에서 확실히 하나가 된다.
- **해결**: `lib/kv-memory.ts` 의 인스턴스를 `globalThis.__to8_memkv__` 에 저장.
- **배운 점**: "서버 프로세스 하나 = 모듈 하나"라는 가정은 개발 서버에서 깨질 수 있다. 프로세스 전역
  상태가 필요하면 처음부터 `globalThis` 로.

## 4. Next.js 16 이 `middleware` 를 deprecated 로 경고

- **문제**: `next dev` 로그에 `The "middleware" file convention is deprecated. Please use "proxy" instead.`
- **시도**: 계속 써도 동작은 함(`proxy.ts: Nms` 로 내부에서 이미 proxy 로 취급). 하지만 제출물은 최신이어야 함.
- **비교**: 파일명·export 이름을 `proxy` 로 바꾸는 것 vs 경고를 안고 가는 것.
- **해결**: `middleware.ts` → `proxy.ts`, `export function middleware` → `export function proxy`.
  `config.matcher` 는 그대로.
- **배운 점**: 프레임워크 메이저 버전이 바뀌면 자동 추가되는 `CLAUDE.md`("This is NOT the Next.js you know")
  같은 신호를 먼저 읽어야 한다.

## 5. `node --test` 가 `@/` 경로를 못 풂

- **문제**: `lib/repository/item.ts` 를 직접 import 하는 단위 테스트가 `Cannot find package '@/lib'`.
- **시도**: tsconfig `paths` 는 타입 검사·번들러용이지 Node 런타임 해석에는 안 쓰인다.
- **비교**: `tsconfig-paths` 의존성 추가 vs import map vs 테스트 범위 조정.
- **해결**: 순수 함수(`lib/domain/rules.ts`, import 없음)는 `node --test` 로, 라우트 규약은 소스 정적 검사
  (`test/routes.test.mjs`, fs 만)로. 저장소 로직의 실제 동작 검증은 실행 서버를 때리는
  `scripts/verify-webauthn.mjs` 가 맡는다.
- **배운 점**: 얇은 도구(`node --test`)를 억지로 늘리기보다, 검증 종류에 맞는 도구를 나눈다.
